\section{Guards, Kernel and Seam Predicates}\label{appendix:guards-system}

Guards, kernel predicates and seam predicates extend GLP programs with access to the GLP runtime state, operating system and hardware capabilities.

\mypara{Predefined types}
The predefined types, available in every GLP program, are \verb|Stream(X)|, \verb|OpenStream(X)|, \verb|DiffList(X)|, \verb|Channel(In, Out)|, \verb|Closed|, \verb|MwmInput(X)|, \verb|Number|, \verb|Constant|, \verb|Key|, \verb|SignedTerm|, \verb|Hash|, \verb|GlobalName|, \verb|Answer|, and the arithmetic-expression type \verb|Exp|; their definitions are in \verb|programs/self.glp| of the public GLP repository. \verb|Integer|, \verb|Real|, \verb|String|, and \verb|Module| are primitive types built into the runtime.

Some predefined types name a structure another already denotes. Type identity being structural, the checker treats such a pair as one type and will accept either where the other is declared; the second name buys no checking. It is declared all the same, for two reasons. It says what a value is for where the structure alone does not --- a key and a hash are both strings and are not the same thing to a reader --- and it localises a later change of representation to one definition rather than to every declaration that would otherwise have named the structure directly.

\mypara{Guard predicates}
Guards provide read-only access to the runtime state of GLP computation. A guard appears after the clause head, separated by \verb=|=, and must be satisfied for the clause to be selected. The ``Ground'' column indicates whether success of the guard implies that the argument is ground; such guards permit multiple occurrences of the reader in the clause body (Remark~\ref{rem:guards-srsw}). Built-in guards can be negated: \verb|~G| succeeds if \verb|G| fails and vice versa, while suspension is unchanged; negation applies only to atomic built-in guards, not to defined guards or conjunctions.

\verb|otherwise| succeeds if all previous clauses for this procedure failed (or suspended).

\verb|=?=| succeeds if both arguments are ground and equal. For example, \verb|f(a,X?) =?= f(b,Z?)| fails (not suspends) because the ground subterms \verb|a| and \verb|b| already differ. Note that the implementation checks terms left-to-right and does not guarantee early failure detection; \verb|f(X?,a) =?= f(Y?,b)| may suspend rather than fail.

\verb|is_mutual_ref| succeeds if its argument is a mutual reference, the handle through which \verb|mwm/2| appends to the tail of its output stream in constant time. It is admitted only to a system module, as are the body kernels that create, append through and close a mutual reference: no other module can obtain one, so no other module can put the guard to use.

\mypara{Arithmetic comparison guards}
Arithmetic comparison guards evaluate their arguments as arithmetic expressions over \verb|+|, \verb|-|, \verb|*|, \verb|//| (integer division), and \verb|mod|, and compare the results. Success implies both arguments are ground.

\mypara{Time guards}
Time guards provide access to the system clock for scheduling and synchronization:

\begin{center}
\begin{tabular}{ll}
\textbf{Guard} & \textbf{Signature} \\
\hline
\verb|wait| & \verb|procedure wait(Number?).| \\
\verb|wait_until| & \verb|procedure wait_until(Number?).| \\
\end{tabular}
\end{center}
\noindent\verb|wait(D)| suspends for \verb|D| milliseconds then succeeds. \verb|wait_until(T)| suspends until the current time is at or past timestamp~\verb|T| (Unix milliseconds), then succeeds. Neither guard can be negated. They are a program's only means of suspending on the clock, as \verb|now/1| below is its only means of reading one.

\mypara{Monotonicity and implications}
\verb|ground/1|, \verb|no_readers/1|, and \verb|known/1| are monotonic. \verb|ground(X)| implies both \verb|no_readers(X)| and \verb|known(X)|, which do not imply each other: \verb|no_readers(X)| succeeds but \verb|known(X)| fails for an unassigned writer; \verb|no_readers(f(X?))| suspends but \verb|known(f(X?))| succeeds.

\mypara{Defined guard predicates}
To support abstract data types and cleaner code organization, GLP provides for user-defined guards via unit clauses. A unit clause \verb|p(T1,...,Tn).| defines a guard predicate; the call \verb|p(S1,...,Sn)| in guard position is unfolded to the term matching of \verb|T1| with \verb|S1|, ..., \verb|Tn| with \verb|Sn|. For example, unification is defined by the unit clause \verb|X? = X.|, so the guard \verb|A = B| unfolds to matching both \verb|A| and \verb|B| against the same variable \verb|X|.

The following defined guard predicates are shipped with the runtime:

\mypara{Naming and admission of body kernels}
A body kernel is named by a quoted constant whose name begins with an underscore, as \verb|'_add'| is. Quoting is necessary: an unquoted name beginning with an underscore is an anonymous variable (Remark~\ref{rem:anonymous-variables}). A module declaring \verb|-mode(system)| may define and call procedures whose names are so written; a module that does not may neither define nor call one. The restriction is on names in call position only; a constant beginning with an underscore is unrestricted as data, as a message tag or a member of a type union. The system modules are the root \verb|programs/self.glp| and the modules under \verb|programs/system/|.

\mypara{Body kernel predicates}
\temph{Body kernel predicates} are runtime-implemented primitives that execute in the clause body with two-valued semantics: they either succeed or abort. Body kernels are not directly accessible to user programs. They are invoked only by the kernel and seam predicates below---predicates defined by GLP clauses that are shipped with the runtime and have privileged access to the body kernel registry. The invoking predicate's own guards ensure that a body kernel's preconditions are met before invocation.

The table below is the interface between GLP and its runtime, and is documentation for the writers of system modules rather than a facility of ordinary programs: no application module may call any of it. Every kernel the runtime registers appears here, whether or not an ordinary program can reach what it does.

\mypara{Kernel and seam predicates}
A predicate defined by GLP clauses whose body may invoke a body kernel is of one of two kinds, and the difference is what lies on the other side of it. A \temph{kernel predicate} reaches the runtime that implements GLP: arithmetic, term structure, the clock, the module system. A \temph{seam predicate} reaches something the language cannot reach at all --- the person, the person's keys, the networking layer, the platform. The first kind is GLP realised; the second is GLP joined to what is not GLP, and a seam is where two things are joined.

The distinction is not one of mechanism: both are ordinary GLP clauses, both may name a body kernel in call position, and both are admitted only to a system module. It decides where the specification of a construct's behaviour belongs. A kernel predicate's behaviour is the language's own and is stated here. A seam predicate's is not: what an address is, what a geofence reports, what a signature attests are settled by the paper that specifies the thing on the far side, and this catalogue states the predicate and cites that paper.

Both tables list those in root scope, where every program reaches them; a system module may define others for its own use, and those belong to that module rather than to the language.

\mypara{Term composition and decomposition (\texttt{=..}, \texttt{..=})}
Composition and decomposition are two predicates, not one bidirectional predicate. A declaration fixes one mode per argument, so a single name cannot carry both directions: \verb|=..| takes a list and produces a term, and \verb|..=| takes a term and produces a list, each with the opposite mode on both arguments. \verb|T =.. [foo, a, b]?| constructs \verb|T = foo(a, b)|; \verb|L ..= foo(a, b)?| produces \verb|L = [foo, a, b]|.

Both are needed, and a program that walks an arbitrary term needs both together: \verb|..=| to take a compound apart and recurse on its arguments, \verb|=..| to rebuild it from the results. Decomposition alone descends without returning, and composition alone cannot get started.

\mypara{Clock access (\texttt{now/1})}
Binds the argument to the current Unix timestamp in milliseconds since the epoch.

\mypara{Arithmetic evaluation and assignment (\texttt{:=})}
Arithmetic assignment is defined recursively: each clause pattern-matches on an arithmetic operator, guards verify that operands are of the required type, and the body invokes the corresponding body kernel. An \verb|otherwise| clause handles the case where operands are themselves expressions, evaluating them recursively before retrying.

\mypara{Seeded random numbers (\texttt{random/4})}
\verb|random(Seed, N, Value, NextSeed)| binds \verb|Value| to a pseudo-random integer with $1 \leq \mathtt{Value} \leq \mathtt{N}$, and \verb|NextSeed| to the seed of the next draw, given a ground seed \verb|Seed| and a ground bound $\mathtt{N} \geq 1$. It is a body goal, not a guard; the clause is guarded by \verb|integer(Seed?), integer(N?), N? >= 1| and invokes the \verb|'_random'| body kernel. \verb|NextSeed| is determined by \verb|Seed| alone; \verb|Value| by \verb|Seed| and \verb|N|. The seed stream is therefore independent of the bound requested, and a computation that threads \verb|NextSeed| from each draw into the next reproduces exactly from its initial seed.

\mypara{Output to the person (\texttt{send\_to\_person/1})}
\verb|send_to_person(Stream)| emits each element of \verb|Stream| to the person operating the agent, in order, and ends when the stream ends. Its clause is guarded by \verb|ground| on the element and invokes the \verb|'_output'| body kernel. A module reaches the person through this predicate; naming \verb|'_output'| in call position is admitted only to a system module.

\mypara{Module as a value (\texttt{self\_module/1}, \texttt{decompose\_module/4})}
\verb|self_module(Module)| binds its argument to the caller's own module, a value of the primitive type \verb|Module|. \verb|decompose_module(Module, Key, Source, Compiled)| takes a module value apart, assigning the public key of the compiler that produced it, the identity of the source it was compiled from, and the identity of the compiled module itself.

The two identities are distinct and neither determines the other. Source identity says what was written; compiled identity says what runs, and two compilers compiling one source produce two of them. The compiler's key is what joins them: it is the compiler that vouches for the correspondence, and a party relying on the pair decides for itself whether that key is one it accepts. A module value is opaque to a program, so the decomposition has to come from the runtime~\cite{keidar2026secure}. Neither identity is the type identity of \verb|run/3| and \verb|find_type/2|, which is a property of a declaration and not of a module.

\mypara{Dynamic activation (\texttt{run/2}, \texttt{run/3}, \texttt{find\_type/2})}
\verb|run(Goal, Module)| activates the module value \verb|Module| and posts \verb|Goal| to it; the predicate of \verb|Goal| must be exported by \verb|Module|, else an error. The readers and writers of \verb|Goal| connect the caller and the activated module. \verb|run(Goal, Type, Module)| activates \verb|Module| and posts \verb|Goal| to it where \verb|Type| equals the type identity that \verb|Module|'s exports record for \verb|Goal|'s predicate, and errs otherwise. \verb|find_type(P/N, Type)| assigns \verb|Type| the type identity of the declaration of \verb|P/N| in the caller's scope, and \verb|error| where \verb|P/N| is not declared there. Type identity is defined in the Typed GLP companion paper~\cite{shapiro2026types}, which also gives its construction and proves the compatibility it rests on. \verb|run/3| and \verb|find_type/2| are not yet implemented.

\mypara{Identity and signature (\texttt{self\_key/1}, \texttt{sign/3}, \texttt{signed/4}, \texttt{signed/2})}
\verb|self_key(Key)| assigns \verb|Key| the public key of the person operating the agent. \verb|sign(Term, Key, Signed)| requires \verb|Term| ground and \verb|Key| a key of that person, and assigns \verb|Signed| the signature under \verb|Key| of the pair of \verb|Term| and the identity of the module making the call. \verb|signed(Signed, Key, Hash, Term)| takes a signed term apart, assigning the signer's key, the identity of the module under which the signature was made, and the term signed; \verb|signed(Signed, Key)| assigns the signer alone, for a reader that needs to know who signed and not what.

The module identity is the runtime's contribution and cannot be the program's, because a program can build any term it likes. Were the signature over \verb|Term| alone, any module the person runs could obtain that person's signature on any statement whatever, and a signature would attest only that the person ran something. Scoped, it says that the person ran this module and that this module asked for this term, which is what a relying party needs~\cite{keidar2026secure}.

A signature is what carries a claim to a party that has neither an authenticated channel to its author nor an attestation of the runtime that produced it. Within a conversation none is needed: authorship of every stream extension is already established to its reader by the channel and by the attested runtime at the writer's end~\cite{keidar2026secure}. It is needed outside one --- a rendezvous agent belongs to no social graph and is itself unattested, and admits a connecting agent on a signed capability and on nothing else~\cite{bachar2026networking}.

\mypara{Held links (\texttt{authorise\_link/2})}
\verb|authorise_link(L, A)| answers a link that the runtime holds and reports because its other end is at an agent with which the name was not exchanged. \verb|L| is the global name of the reported link, of type \verb|GlobalName|, and \verb|A| is of type \verb|Answer|, either \verb|authorise| or \verb|refuse|: on \verb|authorise| the runtime releases the held message or assignment, on \verb|refuse| it drops the link. The clause is guarded by \verb|known(A?)| and invokes the \verb|'_authorise_link'| body kernel. A link end is held when the agent at its other end is not the one with which the name was exchanged; while it is held the runtime places nothing on its channel and applies nothing arriving on it. The decision is the program's rather than the runtime's because the reason to release or drop such a link is not visible to the runtime, which therefore reports and waits. The mechanism that holds a link and reports it is described in the companion implementation paper~\cite{shapiro2026implementing}.

\mypara{Networking seam (\texttt{peer\_address/2}, \texttt{punch\_udp/1}, \texttt{place\_declare/3}, \texttt{place\_remove/1})}
\verb|peer_address(P, A)| assigns \verb|A| the address at which the networking layer observes peer \verb|P|. \verb|punch_udp(A)| opens a path to address \verb|A| and assigns nothing. \verb|place_declare(P, R, E)| declares a place \verb|P| of radius \verb|R|, centred on the declaring agent's location at the time of the call, and assigns \verb|E| a stream of that agent's own \verb|entered| and \verb|exited| events for the place, interleaved with \verb|unobservable| where the layer has stopped reporting crossings and \verb|observable| where it resumes; between the two no crossing is seen and none is delivered late. A further declaration of the same place supersedes the earlier one and closes its stream. \verb|place_remove(P)| ends the declaration of \verb|P|, and does nothing where \verb|P| is not declared. Each clause is guarded by \verb|ground| on the arguments it consumes, and the clauses themselves are in \verb|programs/self.glp|.

The four are on this seam because a GLP program cannot reach the platform by itself. \verb|peer_address/2| is address discovery: an agent behind a NAT learns from a peer the public address that peer observes for it, and \verb|punch_udp/1| opens a path to a peer so observed, the two together standing in for external address-discovery infrastructure. \verb|place_declare/3| and \verb|place_remove/1| register and unregister a geofence with the platform's location service. Crossings reach the program as messages on a stream rather than through a guard, and must: a guard is a test on the resolvent alone, so one that consulted the device's location would let the same local state reduce differently at different times. A declaration carries a name and a radius and returns no coordinates, so a program learns of its own device's location only that it entered or left a place it named itself~\cite{bachar2026networking}. The runtime behind the kernels they invoke is described in the companion implementation paper~\cite{shapiro2026implementing}; the layer beneath that is specified in the networking companion paper~\cite{bachar2026networking}.

\mypara{Proximity trust (\texttt{trust\_declare/2})}
A \emph{proximity medium} carries a \emph{cold-call trust level}, which decides whether the agent answers an unsolicited approach from a device it does not already know. \verb|trust_declare(Medium, Level)| declares that level for one medium: \verb|Medium| is \verb|ble| or \verb|lan| and \verb|Level| is \verb|open| or \verb|closed|. Both media stand at \verb|closed| until declared, a later declaration of a medium replaces the level then standing, and the two are declared independently, so an agent may answer strangers over one and ignore them over the other. The clause is guarded by \verb|ground| on both arguments.

The level is the program's to set and cannot be the layer's, for a reason that decides where the predicate belongs: an agent raises the level on entering a place it trusts and lowers it on leaving, and lowers it again when that place's crossings become unobservable, doubt resolving to closed --- and the layer cannot do any of that, because it does not know which place is trusted. The program declared the place~\cite{bachar2026networking}.

\mypara{Multiway merge (\texttt{mwm/2})}
\verb|mwm(In, Out)| merges the streams named by \verb|In| into the single stream \verb|Out|, preserving the order of each input stream and interleaving them fairly. \verb|In| is a stream of \verb|merge(S)| elements, each contributing the stream \verb|S| to the merge, following the merger of FCP~\cite{shapiro1989family}. Since \verb|In| is itself a stream, a \verb|merge(S)| element arriving later grafts a further stream into a running merge: the set of merged streams need not be known when the merge begins, and a merge is closed by closing \verb|In|.

\verb|mwm/2| is the construct to use whenever many streams are merged into one, and is preferred to a tree of \verb|merge/3| goals for that purpose. The difference is asymptotic, not stylistic. Merging $n$ streams with binary \verb|merge/3| passes each message through $\log n$ merge processes on a balanced tree, and through as many as $n$ on the linear tree a program most easily writes; \verb|mwm/2| appends each message once, in constant time, through a handle on the tail of \verb|Out|. A program that builds its own merge tree pays a factor no implementation can recover, since the cost is in the process structure the program chose. None of this makes a hand-built merge tree wrong: it is sound, and knowing how to build one is worth having. The preference is about which construct a program should reach for when many streams must arrive at one receiver, not about which technique is worth understanding.

\verb|merge/3| remains the right construct where two streams are merged, or where the merge tree itself carries meaning --- a merge goal that is also the point at which a process terminates. \verb|mwm/2| is for many-to-one merging, which is the common case in a program routing many senders to one receiver.

The complete definitions of \verb|:=|, \verb|now|, \verb|=..|, \verb|..=|, \verb|random|, \verb|send_to_person|, \verb|self_module|, \verb|decompose_module|, \verb|run|, \verb|self_key|, \verb|sign|, \verb|signed|, \verb|authorise_link| and \verb|mwm| are in \verb|programs/self.glp| of the public GLP repository.
